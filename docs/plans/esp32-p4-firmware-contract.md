# P4 paired upgrade contract v1

Decision date: 2026-10-11. Update profile `p4-ab-pair-v1`, carried by the
[signed release contract](esp32-firmware-release-contract.md).
This defines releasable candidate assets, not an implemented or qualified
P4 updater. Existing generic A/B support is opt-in/build verified; legacy
devices cannot install these assets without a separate qualified migration.

## P1 - One signed update, two immutable payloads

Publish the exact unsigned, unencrypted ESP32-P4 `aros-esp32p4.bin` core
(chip ID 18, at most
524288 bytes) and its `aros-bsp-ab.bin` (at most 6291456 bytes including
the envelope). Both asset hashes/lengths and their pairing occur in the same
signed manifest. Never mix board builds, release cores, BSPs, ABI consumers or
development/release configurations. Secure-Boot-signed/encrypted core handling
requires a separate qualified profile. Binary structural validation is required
in addition to signature checking; the envelope maker's header/size checks
alone are not full ESP-image or bootability validation.

The existing envelope generated by `tools/make-ab-bsp.py` stays unchanged:

| Byte offset | Content |
| --- | --- |
| 0..7 | `P4ABPKG` followed by binary version byte 1 |
| 8..11 | Complete core byte length, little-endian u32 |
| 12..15 | Raw PKG byte length, little-endian u32 |
| 16..47 | SHA-256 of the complete core |
| 48..79 | SHA-256 of the raw PKG |
| 80..111 | SHA-256 of envelope bytes 0..79 |
| 112..127 | Reserved zero bytes |
| 128 onward | Complete PKG v1, no trailing data |

The envelope binds the pair and detects corruption; it is not publisher
authentication. Release signing covers the complete enveloped BSP, not just
the inner PKG. The loader's ELF/member/relocation audits remain mandatory.
The ESP-IDF C6 app-descriptor contract must not be imposed on the AROS P4 core.

## P2 - Board/layout/ABI qualification

Produce separate update records for `d1001`, `jc1060p470c-v1` and
`jc1060p470c-v2`; a shared asset requires explicit evidence of identical
build compatibility. `p4-ab-256k-v1` identifies the current 256-KiB boot prefix,
512-KiB kernel slots, 6-MiB BSP slots and independent DEVELOP layout.
It is a compatibility requirement, not permission to overwrite the live table.
Actual flash capacity, table, running pair and inactive pair must be detected
and compared; no writes based on build-default offsets or manifest offsets.
P4 legacy raw packages/full-flash migration images are not this upgrade profile.

The manifest binds CPU/SMP/SDK and exact private host/WiFi ABI requirements.
Rebuild and audit the complete dependency closure in the actual BSP; equal
struct size is not semantic ABI compatibility. These private requirements do
not promise vanilla AROS cross-architecture binary compatibility or stable
public ABI. Unsupported/missing board/layout/ABI facts refuse admission.

## P3 - Safe installation boundaries

Verify the signature and both complete immutable assets before mutation.
Require the BSP envelope's core length/hash to match the separately listed
core's actual length/hash, and its inner PKG length/hash and header digest to
match the held BSP bytes. A valid release signature can authenticate a
mistakenly mismatched pair; such a pair must still be refused before any write.
Write only the qualified inactive core+BSP pair. Verify full readback, envelope
and module audits before a crash-consistent boot-selection commit. Never
select a partially written pair. Preserve the active pair, bootloader/table,
NVS, DEVELOP and unrelated upper-flash storage. No automatic fallback to an
in-place legacy update, even when the active image is old.

Installation success requires boot into the expected pair, both-Hart/watchdog,
storage and desktop/touch qualification plus bounded successful-boot
confirmation. Power-loss tests must cover each write/selection/confirmation
boundary and prove rollback. The privileged native flash interface, selection/
confirmation journal, recovery/migration and persistent release-sequence floor
are open work. The current hash-only boot gate does not enforce publisher
signatures against a physical attacker; end-to-end boot trust/Secure Boot is
a separate security project, not a claimed result of signed downloads.

## P4 - GUI, release and acceptance

The P4 GUI shows the actual proportional partition map, active/inactive pairs,
gaps/capacities and proposed write targets. Imported tables are previews, not
live proof. CLI uses the same verifier/admission/backend and presents the same
roles, unknowns and failure results. A normal upgrade offers no bootloader or
partition-table write operation.

Release candidates must pass R4, existing envelope/layout/package tests,
fresh isolated board/layout native builds and dependency audits. Hardware
qualification additionally requires safe native flash ownership under SMP,
readback, power-loss/rollback, confirmation and boot health. CI presently
does not build/release the ESP32 targets; a protected signing job alone cannot
close that gap. Do not publish an unqualified candidate as an installable
stable upgrade or enable an updater from these documents alone.
